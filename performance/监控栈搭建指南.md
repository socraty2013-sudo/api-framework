# Prometheus + Grafana 监控栈搭建指南

> 本笔记以本项目（macOS + Flask 电商系统压测）为落地面，但**写法按可复用设计**：
> 换被测系统、换机器、换部署方式，只需改第六节的对应项，其余不动。

---

## 一、这套东西解决什么问题

压测时你会盯着 `top` 看 CPU。问题在于：

| top 的问题 | 后果 |
| --- | --- |
| 屏幕刷过去就没了 | 压完想回看「第 80 用户那 60 秒 CPU 是多少」，查不到 |
| 只能看当下 | 无法对齐「QPS 掉下来的那一秒，CPU 在干什么」 |
| 没有历史 | 做不了基线和趋势对比 |

**监控栈要解决的就是这三件事：把指标定时采下来、存住、能回放。**

一句话记法：

> `top` 是「此刻的快照」，监控栈是「全程的录像」。

监控的**核心不是实时，是数据有没有被存下来**。

---

## 二、三个组件各干什么

| 组件 | 角色 | 打个比方 | 默认端口 |
| --- | --- | --- | --- |
| **exporter** | 采集器 | 摄像头：把机器/应用的指标变成一串数字，摆在门口等人来取 | 9100 / 9256 / 9115 |
| **Prometheus** | 数据库 + 查询引擎 | 保安：每隔一段时间去各摄像头取一次，存进仓库 | 9090 |
| **Grafana** | 展示 | 电视墙：去仓库里查数据，画成图 | 3000 |

数据流向：

```
被测机器指标 ──► exporter ──(Prometheus 定时拉取)──► Prometheus 存储 ──► Grafana 查询画图
```

### 关键机制：拉（pull）不是推（push）

**Prometheus 是主动去 exporter 拉数据的，不是 exporter 主动发过来。**

这解释了三个日常现象：

1. exporter 挂了 → Prometheus 的 Targets 页面会显示 `DOWN`，这是它发现问题的唯一方式；
2. 网络不通（比如容器之间连不上）→ 表现在 Targets 页 `DOWN`，不是日志报错；
3. `scrape_interval` 决定**采集精度**：设 15 秒，你就只有 15 秒一个点，中间发生什么永远看不到。

> 这和 MQ 的推送模型正好相反。理解这一点，后面所有「为什么没数据」都能自己排查：**先看 Targets 页是不是 UP，再看 Grafana。**

## 三、搭建方案

两种装法，选哪个取决于你的工作环境。

### 方案 A：本机直接装（本项目用的这个）

适合：本机做实验、不想开 Docker。

**macOS（Homebrew）**

```bash
brew install prometheus grafana node_exporter
brew services start prometheus
brew services start node_exporter
brew services start grafana
```

**Linux（Debian/Ubuntu）**

```bash
sudo apt install prometheus prometheus-node-exporter grafana
sudo systemctl start prometheus node-exporter grafana-server
```

**CentOS/RHEL**

```bash
sudo dnf install golang-github-prometheus-prometheus grafana
```

**Windows**

官方无 `node_exporter` 的等价物，装 `windows_exporter`（原名 wmi_exporter）：
从 GitHub `prometheus-community/windows_exporter` 下载 msi，安装后默认监听 9182 端口，配置和 Linux 完全一样，只把 target 的端口换成 9182。

**装完先验证三个端口活着**，再动配置：

```bash
curl -s localhost:9100/metrics | head -5    # exporter 有输出 = 活
curl -s localhost:9090/-/healthy            # 返回 Prometheus is Healthy.
curl -sI localhost:3000 | head -1           # Grafana 返回 HTTP/1.1 302
```

### 方案 B：Docker Compose（跨机器最省事）

适合：换到任何一台装了 Docker 的机器，一条命令全起来。**推荐在真实工作环境用这个**，因为配置写死在文件里，可以提交进 git，团队共用一套。

```yaml
services:
  node-exporter:
    image: prom/node-exporter:latest
    ports:
      - "9100:9100"
    volumes:
      - /proc:/host/proc:ro
      - /sys:/host/sys:ro
      - /:/rootfs:ro
    command:
      - '--path.procfs=/host/proc'
      - '--path.sysfs=/host/sys'
      - '--path.rootfs=/rootfs'

  prometheus:
    image: prom/prometheus:latest
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus-data:/prometheus
    depends_on:
      - node-exporter

  grafana:
    image: grafana/grafana:latest
    ports:
      - "3000:3000"
    volumes:
      - grafana-data:/var/lib/grafana
    depends_on:
      - prometheus

volumes:
  prometheus-data:
  grafana-data:
```

启动：`docker compose up -d`

**两点必须注意：**

1. **node-exporter 那些 `volumes` 和 `command` 是 Linux 专用的。** 容器里的 node-exporter 默认采集的是**容器自己**（也就是 Docker 的虚拟机），不是宿主机。挂载 `/proc`、`/sys` 并告诉它去 `/host/proc` 读，才采得到宿主机。
2. **macOS 上这么做拿到的是 Docker 虚拟机的指标，不是 Mac 的。** Docker Desktop 在 Mac 上是跑在一个 Linux 虚拟机里的，宿主机指标传不进去。所以 **Mac 要采本机指标，只能用方案 A 的 brew 装。**

## 四、prometheus.yml 怎么写

**这是全套里唯一必须手写的配置文件。** 配错就没数据，而且报错不直观。

本机实际在用的（`/opt/homebrew/etc/prometheus.yml`）：

```yaml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: "prometheus"      # 抓自己
    static_configs:
    - targets: ["localhost:9090"]

  - job_name: "node"            # 抓主机
    static_configs:
    - targets: ["localhost:9100"]
```

逐段解释：

| 段 | 含义 | 怎么改 |
| --- | --- | --- |
| `scrape_interval` | 多久抓一次 | 平时 15s；**压测期间改 5s**，否则 4 分钟只 16 个点，曲线糙到看不出拐点 |
| `job_name` | 这组抓取任务叫什么 | 自己起名，Grafana 里按这个名字筛选 |
| `targets` | 去哪个地址抓 | `IP:端口`，多个写多个；跨机器就写被测机的 IP |

### 增量配置：加上新的 exporter

每个 exporter 就是在 `scrape_configs` 里多加一段：

```yaml
  - job_name: "process"          # 进程级指标（仅 Linux）
    static_configs:
    - targets: ["localhost:9256"]

  - job_name: "blackbox"         # 黑盒探活（仅 Linux/Docker 通用）
    static_configs:
    - targets: ["localhost:9115"]
```

### 改完必须做的两件事

**1. 语法校验**（省得重启后起不来还得反复查）：

```bash
promtool check config /opt/homebrew/etc/prometheus.yml
# 期望输出：SUCCESS: ... is valid prometheus config file syntax
```

**2. 重启 + 看 Targets 页**

```bash
brew services restart prometheus        # macOS
sudo systemctl restart prometheus       # Linux
```

浏览器打开 `http://localhost:9090/targets`，每个 job 应该显示 `UP`。

> **Targets 页是监控栈的「体检报告」。** 任何「Grafana 没数据」的问题，第一步都是来这里看：`DOWN` 说明拉不到，`UP` 才说明数据已经在库里了，问题就出在图那边。

### 配置文件到底在哪个路径

不同安装方式位置不同，别死记，用这招找：

```bash
# 1. 从运行中的进程参数里找（对任何程序都有效）
ps aux | grep prometheus | grep -o '\-\-config.file=[^ ]*'

# 2. systemd 管理的看 unit 文件（Linux）
systemctl cat prometheus

# 3. brew 管理的看 plist（macOS）
cat ~/Library/LaunchAgents/sh.brew.prometheus.plist
```

## 五、Grafana：接数据源、导看板

### 第一步：连上 Prometheus

浏览器 `http://localhost:3000`，默认账号 `admin / admin`，首次登录要求改密码。

`Connections → Data sources → Add data source → Prometheus`

**URL 填什么，取决于 Grafana 怎么部署的：**

| Grafana 部署方式 | 数据源 URL |
| --- | --- |
| 本机直接装（本项目） | `http://localhost:9090` |
| Docker Compose | `http://prometheus:9090`（**用服务名，不是 localhost**） |
| Grafana 在本机、Prometheus 在另一台机 | `http://<目标机IP>:9090` |

> **这是最常见的坑**：Docker 里 Grafana 填 `localhost:9090` 一定失败——容器里的 localhost 指的是容器自己，不是宿主机。

点 `Save & test`，显示绿色 `Successfully queried the Prometheus API` 才算连上。

### 第二步：导入现成看板

不用自己画。社区有现成的，导入 ID 即可。

`Dashboards → 右上角 New → Import → 输入 ID → Load → 选择 Prometheus 数据源 → Import`

| 看板 ID | 名称 | 内容 |
| --- | --- | --- |
| **1860** | Node Exporter Full | 主机全套指标（CPU/内存/磁盘/网络），最常用 |
| 3662 | Prometheus 2.0 Overview | Prometheus 自身状态 |
| 4475 | Node Exporter（精简版） | 面板少，新人看着不晕 |

**打开 1860 后会有很多面板是空的。** 这是正常的——那些指标当前平台不支持（本项目 macOS 上就没有 swap、部分内存细节）。**空白不是配错了，是采不到。**

### 第三步：只看四张

1860 有几十张图，第一次看必然懵。压测时只关心这四张：

| 指标 | 看板位置 | 判读 |
| --- | --- | --- |
| CPU | CPU Basic → CPU Usage | 接近 100% = CPU 瓶颈 |
| 内存 | Memory Basic → Memory Usage | 持续上涨不回落 = 泄漏 |
| 磁盘 IO | Disk → Disk I/O | 高 = 落盘瓶颈 |
| 网络 | Network Traffic | 达到带宽上限 = 网络瓶颈 |

## 六、换环境怎么改（★ 复用核心）

这一节是全篇最有用的部分。**搭建动作永远一样，变的只有「采什么」和「从哪采」。**

### 6.1 被测系统不是 Flask

这是最容易卡住的地方。核心原则一句话：

> **监控栈只认「HTTP 上暴露 /metrics 的地址」，不认你用什么框架。**

所以问题变成：**怎么让被测系统暴露 /metrics。** 三种做法，按侵入性从高到低：

**做法 1：应用自己埋点（有代码权限时首选）**

| 框架 | 依赖 | 暴露的路径 |
| --- | --- | --- |
| Spring Boot | `micrometer-registry-prometheus` | `/actuator/prometheus` |
| Flask | `prometheus-flask-exporter` | `/metrics` |
| Django | `django-prometheus` | `/metrics` |
| Node/Express | `prom-client` | 自己注册 `/metrics` |
| Go | `promhttp` | 自己注册 `/metrics` |

好处：能拿到**业务指标**——接口 QPS、错误率、响应时间分布。这些主机监控永远给不了。

坏处：要开发配合改代码。**测试提需求时就说「请加 Prometheus 端点」，这是行业通用语言，开发一听就懂。**

**做法 2：无侵入探活（blackbox_exporter）**

没有代码权限，也不想让开发改，就用它。它**从外部发请求**，测的是「这个 URL 通不通、多久返回」。

```yaml
  - job_name: "blackbox"
    metrics_path: /probe
    params:
      module: [http_2xx]
    static_configs:
      - targets:
          - http://被测系统:8080/api/products
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: 127.0.0.1:9115
```

能拿到：可用性、响应时间、状态码。**拿不到：内部耗时拆解、业务量。** 但压测摸底足够用。

**做法 3：中间件 exporter（测的对象是中间件时）**

| 中间件 | exporter |
| --- | --- |
| MySQL | `mysqld_exporter`（端口 9104） |
| Redis | `redis_exporter`（端口 9121） |
| Nginx | `nginx-prometheus-exporter`（端口 9113） |
| MQ（RabbitMQ） | 内置 `rabbitmq_prometheus` 插件（端口 15692） |

这些是独立程序，装好配置完即可，**不需要碰业务代码**。

**选型速记：**

```
有代码权限、要业务指标  → 做法 1（应用埋点）
没代码权限、只要通不通  → 做法 2（blackbox）
测的是中间件            → 做法 3（专用 exporter）
```

### 6.2 测试机不是 macOS

| 项 | macOS | Linux | Windows |
| --- | --- | --- | --- |
| 主机指标 | `brew install node_exporter` | `apt install prometheus-node-exporter` | `windows_exporter`（9182） |
| **进程级指标** | ❌ **没有现成方案** | ✅ `process-exporter`（9256） | 需第三方工具 |
| Docker 采宿主指标 | ❌ 只能采到 VM | ✅ 挂载 /proc 等 | 需特殊处理 |

**进程级指标在 macOS 上为什么做不了：**

`process-exporter` 的工作方式是读 `/proc/<pid>` 目录拿每个进程的 CPU、内存。**macOS 没有 `/proc` 这个目录**，所以这条路走不通。

node-exporter 虽然有 `--collector.processes` 开关，但：
- 它给的是进程**数量**统计，不是每个进程的消耗；
- Homebrew 编译版本里常常没启用这个 collector。

所以本项目当初的结论是：**Mac 上想在 Grafana 里看「Flask 进程占了多少 CPU」，没有现成组件。** 只能靠 `top` 或脚本自己采。

**到了 Linux 上，这件事就变简单了**——装 `process-exporter`，配一段抓取，Grafana 里就有每个进程的曲线。

> **这就是「测试机不是 mac」最实质的差异。** 其它都一样。

### 6.3 监控机和被测机不是同一台

真实工作环境里几乎都是这样：**测试机在 A，被测系统跑在 B 的服务器上。**

改两处：

1. `prometheus.yml` 的 target 写成被监控机的 IP：`targets: ["192.168.1.20:9100"]`
2. 确认**防火墙放行** 9100 端口（Linux 上是 `firewalld` / `ufw`，这一步经常被忘）

被监控机上装 exporter 即可，Prometheus 和 Grafana 只装在测试机一侧。

**好处**：CPU 数据不再混入压测工具自身的消耗。本项目是单机压测，所以报告里必须注明「CPU 观测值含压测工具消耗」，就是这条的代价。

### 6.4 端口被占用怎么办

| 组件 | 默认端口 | 改法 |
| --- | --- | --- |
| node-exporter | 9100 | 启动参数 `--web.listen-address=:9200` |
| Prometheus | 9090 | 启动参数 `--web.listen-address=:9091` |
| Grafana | 3000 | `grafana.ini` 里 `http_port = 3001` |

改完端口，记得**两头一起改**：exporter 换端口后，`prometheus.yml` 里的 target 也要跟着变。

## 七、压测时看什么、怎么串结论

监控不是摆着好看，**它是压测结论的证据链**。

本项目那次的判读逻辑，可以直接套用：

| 监控现象 | 说明什么 | 下一步查什么 |
| --- | --- | --- |
| 整机 CPU 接近 100% | 算力吃满 | 是哪个进程吃的？（进程级） |
| 整机 CPU 低、但 QPS 上不去 | **不是硬件问题** | 看应用进程吃了多少核 |
| 应用进程吃了 2 核、整机 10 核 | 应用没在并行 | 查部署方式（单进程/线程模型） |
| 内存持续上涨不回落 | 疑似泄漏 | 加长时间跑稳定性 |
| 磁盘 IO 打满、CPU 不高 | IO 瓶颈 | 查数据库/日志写入 |

**核心方法论：监控数据的作用是「排除」，不是「确认」。**

- CPU 没打满 → 排除 CPU 瓶颈
- 进程 CPU 高 → 排除 IO 等待
- 一圈排完，剩下的就是答案

这和压测报告第五节的排除法链条是一件事。

## 八、常见坑

| 坑 | 现象 | 原因 / 解法 |
| --- | --- | --- |
| YAML 缩进错 | `cannot unmarshal !!str 'targets...' into struct` | `targets` 前面必须空两格再跟 `-`，改完先 `promtool check config` |
| Docker 里填 localhost | Grafana 数据源 Save 失败 | 容器内用服务名：`http://prometheus:9090` |
| Targets 页 DOWN | Grafana 一条数据都没有 | 先解决 DOWN，别去看图 |
| 曲线很糙 | 看不出拐点 | `scrape_interval` 改 5s（压测期间） |
| 看板大量空白 | 以为配错了 | macOS 采不到那些指标，正常 |
| 改配置没生效 | 还是老数据 | 忘了重启 Prometheus（`brew services restart prometheus`） |
| 采到的是虚拟机指标 | Mac 上 Docker 方案 | Docker Desktop 在 Mac 上跑在 VM 里，本机指标要用 brew 装 |
| 时间对不上 | 图和压测时间差几分钟 | 检查两台机器时间同步（`chronyc` / `hwclock`） |

## 九、面试题

#### Q1（场景）：面试官问「你们压测的时候，服务器资源怎么监控的？」

**考点：** 监控栈组成 + 拉模型 + 工具选型

**答：** Prometheus + Grafana，主机指标用 node_exporter 采集，Prometheus 定时拉取存下来，Grafana 导入现成看板展示。压测时主要看 CPU、内存、磁盘 IO、网络四组，配合压测工具的 QPS 和响应时间曲线对齐时间轴，判断瓶颈在资源层还是应用层。

**面试时说：**

> 我们用 Prometheus 加 Grafana。node_exporter 采主机指标，Prometheus 每 15 秒拉一次，Grafana 用现成模板展示。压测时对齐时间轴看 CPU、内存、IO、网络四条线，跟 QPS 曲线一起判断瓶颈在哪一层。压测窗口会把采集间隔调到 5 秒，不然点太稀看不清拐点。

---

#### Q2（锚点·快速自测）：Prometheus 是拉数据还是收数据？这个设计带来什么影响？

**考点：** pull 模型 + 排障思路

**答：** 拉。Prometheus 主动定期去 exporter 的 `/metrics` 端点取数据。好处是采集目标的状态一目了然——Prometheus 那边有个 Targets 页面，每个目标显示 UP 还是 DOWN；坏处是网络不通时它只会显示 DOWN，不会在业务日志里报错。

所以遇到「Grafana 没数据」，排查顺序固定：先看 Targets 页是不是 UP，再看 Grafana 查询和时间范围。

**面试时说：**

> 是拉模型，Prometheus 主动去 exporter 上拉。这个设计的好处是它的 Targets 页面能直接反映被监控目标的存活状态，UP 还是 DOWN 一眼看到。所以排障顺序是反过来的：先确认 Targets 是 UP，说明数据在库里了，再去 Grafana 找图的问题。

---

#### Q3（场景）：Grafana 里主机监控有数据，但想看「我们的 Java 服务占了多少 CPU」，怎么办？

**考点：** 主机监控 vs 进程监控 + 平台差异

**答：** 需要额外组件，主机级 exporter 给不了进程级数据。

Linux 上用 `process-exporter`，它读 `/proc` 目录拿到每个进程的消耗，端口 9256，配一段抓取就能在 Grafana 里看到。

macOS 上做不了，因为 macOS 没有 `/proc` 目录，process-exporter 无从读起。

如果更进一步，想要**业务指标**（接口 QPS、错误率），那就得让应用自己暴露——Spring Boot 加 `micrometer-registry-prometheus` 依赖，就有 `/actuator/prometheus` 端点，里面包含 JVM 状态和 HTTP 请求统计。

**面试时说：**

> 主机指标和进程指标是两回事，node_exporter 只到主机层。要看具体某个进程，Linux 上装 process-exporter，它读 /proc 拿进程消耗。要到业务层就更有用了——Spring Boot 接 micrometer 之后有 /actuator/prometheus，能直接拿到接口维度的 QPS 和耗时分布，比从主机层猜准得多。

---

#### Q4（锚点·快速自测）：监控里怎么看「瓶颈是不是硬件」？

**考点：** 资源指标判读 + 排除法

**答：** 看 CPU、内存、IO、网络四个维度有没有一个打满。

关键是要区分**整机占用**和**单个进程占用**：整机 10 核，如果 CPU 只到 54%，说明硬件有余量；但如果那个应用进程自己吃满了 2 核，说明是它在内部卡住，不是机器不够。

判断链就是：整机能吃满 → 硬件瓶颈；整机吃不满但单进程吃满 → 应用层瓶颈（单进程模型、线程数限制、锁竞争之类）。

**面试时说：**

> 先看整机 CPU 有没有打满，没打满就基本能排除硬件。这时候要看进程级：如果应用进程已经把两三个核吃满，而整机还有大把核闲置，那就不是机器不行，是应用没用上多核——大概率是单进程部署或者线程模型受限。这个判断直接影响建议：是加机器还是改部署方式。

#### Q5（场景）：换一个项目，被测系统是 Spring Boot 的，监控要怎么搭？

**考点：** 方案可迁移性 + 选型判断

**答：** 基础三段不变：Prometheus 加 Grafana，主机指标 node_exporter。变的只是「应用指标怎么采」。

Spring Boot 有现成的：加 `micrometer-registry-prometheus` 依赖，暴露 `/actuator/prometheus`，Prometheus 加一个 job 抓这个端点即可。**这一步需要开发配合**，也是测试提需求的正规说法。

如果拿不到代码权限，就退一步用 `blackbox_exporter`，从外部探活，能拿响应时间和可用性，拿不到内部拆解。

**面试时说：**

> 主机那一段是通的，换项目不用动。区别在应用指标：Spring Boot 接 micrometer 就有 /actuator/prometheus，加个抓取任务就能拿到接口 QPS 和耗时。这一步要开发配合加依赖。如果拿不到代码权限，就用 blackbox_exporter 从外面探，保底能拿到响应时间和可用性。
