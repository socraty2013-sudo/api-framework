| 测试类型 | 阶梯加压（递增负载） |
| 测试日期 | 2026-11-14 |
| 测试工具 | locust 2.34.0 |
| 报告版本 | v1.0 |

---

## 1. 测试背景与目标

被测系统是一套基于 Flask + SQLite 开发的模拟电商系统，运行于本地开发环境。

本次压测回答两个问题：

1. `GET /` 商品列表页的容量上限是多少；
2. 瓶颈落在哪一层。

**压测边界：**

- 只覆盖 `GET /` 读接口，写接口（商品添加、下单、支付）未覆盖；
- 压测机与被测机为同一台机器，监控数据包含压测工具自身消耗；
- 被测应用为 Flask 开发服务器单进程部署，非生产级部署；
- 仅执行 4 分钟阶梯加压，未做长时间稳定性测试。

因此本报告结论仅代表当前开发环境的处理能力，不作为生产容量依据。

## 3. 测试场景

| 项 | 值 |
| --- | --- |
| 压测接口 | `GET /` |
| 接口行为 | 查询商品全表 + 渲染 `product_list.html`，响应体约 5.4 KB |
| 用户行为 | 无思考时间，请求返回后立即发起下一次请求 |
| 加压策略 | 阶梯加压，10 → 20 → 40 → 80 用户 |
| 每级时长 | 60 秒（累计 60 / 120 / 180 / 240 秒） |
| 爬坡速率 | 每秒 5 / 10 / 10 / 20 用户 |
| 总时长 | 240 秒 |
| 数据粒度 | 每秒采样一次时间序列 |

**设计说明：**

- 取消思考时间（`wait_time`）：本次目标是摸系统容量上限，保留思考时间测到的是业务节奏，不是系统极限。
- 用户数等比翻倍：快速覆盖较低负载到过饱和区间。
- 每级 60 秒：低于 30 秒仍处于爬坡阶段，取不到稳态数据；本系统 10 秒即可进入稳态（10/20/30 秒窗口差异小于 1%）。
- 爬坡速率控制在每级时长的 1/5 以内，为稳态留足采样窗口。

## 4. 测试结果

### 4.1 总览

共发起请求 **236402** 次，失败 **0** 次，失败率 **0%**。

> 数据取自 `shape_stats.csv`。locust 终端汇总显示 236434 次，与 CSV 相差 32 次，为汇总时点与落盘时点不同所致，指标一致。

| 指标 | 值 |
| --- | --- |
| 全周期平均 QPS | 984.49 |
| 平均响应时间 | 37.86 ms |
| P50 | 25 ms |
| P95 | 94 ms |
| P99 | 100 ms |
| 最大响应时间 | 140.54 ms |

### 4.2 各级稳态表现

各用户数阶段取该级最后 20 秒数据（已排除爬坡过渡段）：

| 用户数 | 稳态 QPS | P50 | P95 | P99 | 反推 RT（并发 ÷ QPS） |
| --- | --- | --- | --- | --- | --- |
| 10 | 1194 | 8 ms | 12 ms | 14 ms | 8.4 ms |
| 20 | 932 | 10 ms | 26 ms | 29 ms | 21.5 ms |
| 40 | 889 | 19 ms | 49 ms | 55 ms | 45.0 ms |
| 80 | 909 | 24 ms | 93 ms | 100 ms | 88.1 ms |

### 4.3 结果描述

10 用户时 QPS 达到峰值 1194。继续增加并发至 20、40、80，QPS 未继续上升，回落并稳定在 890-930 区间。

同期响应时间随并发递增：反推 RT 由 8.4 ms 增至 88.1 ms，P99 由 14 ms 增至 100 ms。

### 4.4 监控数据

| 指标 | 观测值 | 说明 |
| --- | --- | --- |
| 整机 CPU | 峰值 54.5%，无平台期，压测结束后回落 | 全程未接近 100% |
| 内存占用 | 稳定在 20% 左右 | 无增长趋势 |
| Flask 进程 CPU | 约 217%（约 2 核） | 压测期间 top 观测 |

> 上述监控数据为 Grafana 与 top 的观测值，未做逐秒落盘采集。

## 5. 瓶颈分析

### 5.1 现象

并发由 10 增至 80 后，QPS 由 1194 降至 909，反推响应时间由 8.4 ms 线性增至 88.1 ms。

该现象符合过饱和特征：继续增加并发后吞吐不再提升，新增请求在队列中排队，表现为响应时间随并发近似线性增长。由于 RT 与并发呈线性关系而 QPS 保持恒定，可判定系统在此区间已达到处理能力上限。

### 5.2 排除硬件资源

整机 CPU 峰值 54.5%，内存稳定在 20%，均未接近上限。

若瓶颈位于硬件资源，应观测到 CPU 或内存持续打满。实际两条指标均留有充足余量，可排除硬件资源瓶颈。

### 5.3 排除 IO 等待

若请求阻塞在磁盘或数据库 IO，进程应处于等待状态、CPU 占用维持在较低水平。

实际压测期间 Flask 进程 CPU 占用约 217%（约 2 核），说明处理能力消耗在计算而非 IO 等待。SQLite 为本地文件库、商品表数据量小，查询耗时在毫秒级，不构成阻塞点。

### 5.4 推断

瓶颈位于应用层的并发模型。

Flask 开发服务器（Werkzeug）为单进程多线程模型。在 CPython 解释器中，同一进程内同一时刻仅允许一个线程执行 Python 字节码（GIL），多线程无法真正并行利用多核。因此该进程的 CPU 占用上限约等于 1-2 核，与实测 217% 吻合。

这解释了整机 10 核中约 9 核闲置、QPS 却无法提升的现象。

> 本结论为基于旁证推导的**推断**，未通过 Gunicorn 部署做直接验证。

### 5.5 验证方式（待执行）

部署方式由开发服务器改为 Gunicorn 多进程：

```bash
gunicorn -w 4 -b 127.0.0.1:5050 app:app
```

若 QPS 随 worker 数近似线性提升（4 worker 预期约 4 倍），则 5.4 节推断成立；若 QPS 无明显提升，则瓶颈另在他处，需转向 SQLite 锁竞争、模板渲染等方向继续排查。

## 6. 结论与建议

### 6.1 结论

| 项 | 结论 |
| --- | --- |
| 当前容量 | `GET /` 接口在本环境容量上限约 1200 QPS |
| 瓶颈位置 | 应用层并发模型（单进程 + GIL），非硬件资源 |
| 可承载并发 | 10 并发为最佳工作点，超过后吞吐下降、延迟上升 |

### 6.2 建议

1. **部署方式改为多进程**：使用 Gunicorn/uWSGI，worker 数按 CPU 核数配置。预期 QPS 随 worker 数近似线性提升。
2. **首页增加缓存**：商品列表变更频率低，适合缓存，可降低数据库与模板渲染开销。
3. **补充测试**：当前仅覆盖读接口与 4 分钟短时压测，建议补充写接口压测与长时间稳定性测试，覆盖内存泄漏、连接池耗尽等场景。

## 7. 风险与局限

| 局限 | 对结论的影响 |
| --- | --- |
| 压测机与被测机同机 | CPU 观测值含压测工具自身消耗，应用实际占用低于 54.5%；分离部署后容量上限可能更高 |
| 使用 Flask 开发服务器 | 结论不适用于 Gunicorn/Nginx 等生产部署形态 |
| 仅覆盖 `GET /` 读接口 | 写接口、事务、并发写性能未验证 |
| 累计运行 240 秒 | 未覆盖内存泄漏、连接池耗尽、长时间高负载下的性能衰减 |
| 端口耗尽经 sysctl 调优后规避 | 未保留调优前后的完整对照基线 |
| 未执行多轮取中位数 | 本次为单轮结果。相同配置的历史一次运行（240162 请求 / 1000.04 QPS）与本轮（236402 请求 / 984.49 QPS）偏差 1.6%，结果具备可重复性 |
